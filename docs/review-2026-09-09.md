# Peasy product, code and security review — 9 September 2026

Reviewed revision: `78552c6` (`build fix`). This is a source review with targeted local validation, not a penetration test or a claim that every desktop/hardware flow works. Application code was not changed. Findings marked **reproduced** were exercised with synthetic data or read-only evaluation; other findings follow from the inspected implementation.

Peasy has a sound foundation. Its strongest feature is the separation between interpreting a request and executing an authorized, narrowly defined change. The next development cycle should improve recovery, package identity, onboarding and feedback before expanding the action catalogue.

## What Peasy does

- A shared Rust client powers the GTK/libadwaita UI and CLI. It interprets requests through OpenAI or local Ollama and passes typed decisions through an import-free Wasm policy engine.
- Package installation searches Nixpkgs, evaluates candidates and proposes changes to a canonical managed NixOS module. A bounded follow-up loop can search alternatives. AppImages come from GitHub release discovery and are pinned by hash.
- The system-configuration pea can combine packages with a small reviewed catalogue of services and user groups, including libvirt, printing, scanning and Bluetooth.
- GNOME and Plasma have explicit appearance adapters. Hyprland has bounded session controls. Unsupported desktop features are rejected explicitly.
- Wi-Fi and Bluetooth use local desktop tools. Calendar actions prepare a private iCalendar file and hand it to the default application for import.
- System changes require review and daemon-side administrator authorization. NixOS builds and a separate activation helper apply the result; generation reconciliation restores managed state during rollback.
- The project also supplies a tray launcher, configuration export, an installer integration and ISO release infrastructure.

## What is well written

**Authorization belongs to the service.** Direct IPC does not bypass Apply authorization. Tokens are random, expire, belong to a UID, bind the proposed change to its base state, and cannot be replayed. Polkit subjects include PID, UID and process start time. See [server.rs](../crates/peasy-system/src/server.rs) and [authorization.rs](../crates/peasy-system/src/authorization.rs).

**The model has a small capability surface.** There is no general shell, arbitrary Nix expression or model-selected executable. Closed enums, unknown-field rejection, independent validation and a Wasm guest with no imports make the restrictions concrete. The [Wasm host](../crates/peasy-engine-host/src/lib.rs) limits memory, fuel and output as well.

**The Nix state model is understandable.** One canonical generated file is easier to reason about than competing configuration databases. Renderers escape interpolation; builds check that the resulting generation contains the expected managed state. Setup removal tracks contributions and retains shared dependencies. See [core](../crates/peasy-core/src/lib.rs) and [system configuration](../peas/system_configuration/types.rs).

**Cancellation received real engineering attention.** The atomic transition between cancellation and activation is a good design. Process-group termination accounts for descendants holding pipes open, and window lifetimes are separate from operation lifetimes. The tests exercise races and cleanup rather than only matching strings. See [cancellation.rs](../crates/peasy-core/src/cancellation.rs), [process.rs](../crates/peasy-core/src/process.rs) and [UI tasks](../crates/peasy-ui/src/tasks.rs).

**Credential handling is restrained.** Key-file reads check the opened file, reject symlinks and unsafe permissions, and bound input. Active provider keys are redacted and zeroized. Wi-Fi passwords use a separate local field and stdin rather than command-line arguments. Local Ollama rejects non-loopback origins and ignores proxies.

**The integration tests target useful failures.** The repository includes actual desktop application-discovery regressions, tray recovery, export-dialog checks, installer tests, a production-sandbox VM and a shared native/model/Wasm contract corpus. That is substantially better evidence than unit tests alone. Existing release reports clearly state their hardware and interactive-testing limits.

## Findings to prioritize

### 1. Export is not reliably restorable — high priority, reproduced

The [generated restore wrapper](../crates/peasy-ui/src/main.rs#L592) sets `hostConfiguration` to `/etc/nixos/configuration.nix`, but `managedModule` to `/etc/nixos/host/.peasy/peasy-managed.nix`. The [NixOS module assertion](../nix/module.nix#L217) requires that managed path to be inside the configured host directory's `.peasy/` directory.

A read-only evaluation against the locked Nixpkgs input returned exactly:

```text
services.peasy.managedModule must be inside the host's .peasy directory
```

The current export unit test copies a dummy Peasy module and verifies output files, so it cannot catch this integration failure. Export also explicitly rejects flake hosts, despite the broad “complete NixOS configuration” UI wording.

**Improve:** choose one consistent restore layout; evaluate the actual generated export against the real Peasy module; then add a disposable restore/build test. Expose export limitations in the UI. Preserve a pinned host package source if the product intends export to recreate exact software versions: copying Peasy's own `flake.lock` does not, by itself, pin a traditional host rebuild's Nixpkgs input.

### 2. Export can include credentials despite its assurance — high priority, reproduced

The [settings UI](../crates/peasy-ui/src/main.rs#L326) says “Credentials are not included.” However, [the recursive copier](../crates/peasy-ui/src/main.rs#L651) copies all readable regular files and directories under the host configuration tree. It does not exclude `.env`, `.git`, backups or files containing inline secrets.

A temporary Rust harness using the production export functions confirmed that a synthetic `.env` credential and `.git/config` were included. No actual credentials were inspected or exported. Peasy's separately stored API key is normally outside this source tree, and exported permissions are private; this finding concerns unsafe sharing expectations, not automatic transmission.

**Improve:** replace the absolute assurance with an accurate explanation that host files may contain private values. Show an export inventory, offer exclusions, and distinguish a private backup from an export intended for sharing. Do not promise a secret scanner can prove arbitrary Nix source safe to share.

### 3. Daemon upgrades can leave old code and package metadata active — high priority, source finding

The [service](../nix/module.nix#L431) deliberately disables restart/stop on change so its own activation cannot terminate the initiating operation. It also starts with a fixed Nixpkgs store path. A successful host upgrade therefore does not necessarily replace the running daemon, its configured paths or its lookup caches.

The documentation acknowledges the need for an explicit restart. Operationally, this means a deployed fix may not be running, while the new UI and active system describe a newer generation.

**Improve:** expose daemon build identity, protocol version and package-source identity in Status. Detect mismatches and arrange a controlled restart after an operation has completed and its result has been delivered or recorded. Invalidate outstanding proposals across the transition.

### 4. Lookup and installation can use different package definitions — high priority for correctness, source finding

[Package lookup](../peas/packages/system.rs#L202) imports the Nixpkgs source with `system`, without the host's configured overlays and package options. The generated installation instead uses the host's `pkgs`. Thus the same attribute can have a different version or definition at installation, and host-specific packages may not be discoverable. Unfree/package-policy differences can also affect lookup.

The [package proposal](../crates/peasy-core/src/lib.rs#L453) records the attribute and display name, not an exact derivation identity. The built-state check compares managed declarations, which does not detect a changed definition behind the same attribute. This is a review-integrity issue; administrator-authored overlays remain trusted and this is not a demonstrated privilege escalation.

A read-only evaluation of the locked source demonstrated the mechanism: plain `hello.version` returned `2.12.3`, while a synthetic host overlay returned `review-overlay-version` for the same attribute. This was a package-set demonstration, not an end-to-end installation or a build of that synthetic version.

**Improve:** obtain bounded candidate metadata from the effective host package set. Bind review to the derivation/version and relevant source identity, and invalidate the review if those change before Apply. Upstream [Nixpkgs documentation](https://nixos.org/manual/nixpkgs/unstable/index.html) confirms that NixOS overlays do not automatically affect separate package-set imports.

### 5. Recovery handles returned errors better than abrupt daemon death — high priority for reliability, source finding

[Apply writes the proposed managed module before building](../crates/peasy-system/src/nix_backend.rs#L284). Ordinary error and cancellation paths restore the previous value, but that rollback logic cannot run if the daemon is killed. Startup loads the managed file without reconciling an interrupted transaction. A service crash/restart during the build can consequently leave desired state ahead of the running generation.

Rollback activation normally reconciles generation state, so this is not a claim that every reboot leaves the same problem. Separately, activation failure restores the source file even though system activation may already have changed some live state. An in-process mutex also does not serialize an administrator's independent rebuild against Peasy's build.

**Improve:** add explicit transaction recovery that compares the intended, built and active generations. Record enough information to explain an interrupted operation without inventing a second authoritative configuration database. Detect concurrent source/generation changes. Add fault-injection coverage for daemon termination after the source write and for activation failure after partial progress. Show a recovery action and known-good generation instead of only an error string.

### 6. Removing a disappeared package can be blocked by verifying it first — medium priority, source finding

[Preview](../peas/packages/system.rs#L299) and [Apply](../crates/peasy-system/src/nix_backend.rs#L185) verify an ordinary Nixpkgs package even when removing it. If an update deletes or renames its attribute, the reference that needs removing can fail verification before removal is proposed.

**Improve:** validate removal against the canonical managed state and syntax. Require current derivation existence for installation, not for withdrawing an obsolete declaration. Add a regression with an installed attribute absent from the new package set.

### 7. Submission and progress need stronger UI state — medium priority, source finding

The prompt disables Send while resolving, but the [entry's Enter handler](../crates/peasy-ui/src/main.rs#L924) directly emits `clicked`; the callback has no independent busy guard. The installed GTK binding implements `emit_clicked` as direct signal emission. This permits another resolution worker to be started while one is in flight, potentially duplicating provider calls and allowing competing results to replace the view. This path was inspected, not exercised in a graphical session.

[Apply progress](../crates/peasy-ui/src/main.rs#L1091) is based on elapsed time. It can say “Still building” while authorization or activation is the actual wait. Package selection calls `select` rather than forwarding the available `select_with_progress` stages, so an AppImage download is presented as generic preparation.

**Improve:** use one guarded submission function for mouse and keyboard, with operation IDs to reject superseded results. Stream actual bounded stages: awaiting authentication, resolving, downloading, building, activating, completed. Provide a visible Cancel action before activation and explain when it becomes unavailable.

### 8. Wi-Fi matching silently resolves ambiguity — medium priority, source finding

[Wi-Fi proposal creation](../peas/wifi/client.rs#L18) compares names case-insensitively, sorts matches and takes the first. Two distinct names such as `Cafe` and `cafe` can therefore resolve to the wrong choice, even if the user supplied an exact spelling. Discovery also collapses entries by name, losing distinctions between access points/security modes.

**Improve:** prefer exact matches and present a choice when normalization is ambiguous. Show the actual security mode and distinguish relevant access points rather than silently selecting. This is an avoidable selection weakness, not evidence of credential theft or a complete evil-twin attack.

## Improvements with the greatest user benefit

1. **Make first use work without a configured model.** Today every natural-language request first needs daemon access and model interpretation. With OpenAI selected, connecting Wi-Fi requires an existing route to the provider. Add direct local network controls and a preflight screen for service access, provider readiness and connectivity. Keep explicit package browsing/removal available independently of AI when feasible.
2. **Make the review understandable before showing Nix.** Lead with app, source, version, affected scope, services and permissions. Put the raw diff behind an expandable detail view. Clearly distinguish a system generation change from a session action or a calendar handoff.
3. **Make search fast on the first query.** Existing observations were about 77 seconds on a host and 304 seconds in a constrained VM, not new benchmarks from this review. A cache of query results helps repeat queries but not first use or new searches. Build/cache a searchable metadata index tied to the effective package-set identity, with bounded exact verification before review.
4. **Give success and failure useful next actions.** An installed-app list should distinguish Peasy-managed from administrator-managed packages. Offer Open for applications with verified desktop entries, Review again for expired proposals, Retry for transient failures, and Copy diagnostics for support. Preserve the request and selection after a recoverable failure.
5. **Improve discovery and scope.** Show a few examples appropriate to the desktop, capability availability and clear system-versus-user scope. Appearance is currently a system-generation operation synchronized to user sessions; users should see that scope before an apparently personal preference change.
6. **Explain provider privacy at setup.** The boundary is constrained, but it includes package names and the generated managed state, which can contain account names/UIDs for group contributions. Explain this plainly and provide a way to inspect the outgoing context. Credential keyword detection also rejects benign requests such as asking how to change a password; route such cases to useful local guidance.

## Security posture and engineering follow-up

I found no obvious model-to-arbitrary-command path in the reviewed implementation. The strongest immediate privacy issue is the export assurance. The upgrade and package-identity findings matter because they can undermine what users believe they have reviewed or deployed.

AppImage hashes pin bytes, but neither GitHub search ranking nor a computed hash authenticates an upstream publisher. The default review-only policy is an explicit product choice, and the existing optional allowlist is useful. Improve the source/publisher explanation and avoid treating “Best match” as a trust endorsement. The download limit currently checks release metadata before delegating the fetch; consider enforcing actual transferred size too, since metadata may change between discovery and download.

The pea layout and shared client are worth retaining. The largest maintenance opportunity is separating the approximately 1,600-line UI file into views, operation state and export logic, and separating provider/storage concerns in the client. Avoid a broad rewrite of the small typed policy and privileged interfaces.

The only checked-in GitHub workflow runs on tags or manual dispatch. Add a pull-request fast path for formatting, Clippy, Rust tests and the contract checks, plus a scheduled/current dependency audit. The release workflow has substantial integration coverage, but it does not invoke the full `scripts/check-release.sh` audit/lint sequence. Add realistic end-to-end tests with a fake model provider for authentication denial/retry, duplicate Enter, proposal expiry, completed installation and recovery; retain real hardware acceptance for Wi-Fi/Bluetooth.
